Lesson Studio 01

Make Serenity X smaller, safer, and easier to explain.

Serenity X is not one feature. It is a desktop shell, an app registry, a window lifecycle, application code, several storage systems, and browser resources. You will take control of it one vertical slice and one reviewed decision at a time.

Purpose and stakes

Can you safely change a system you can explain?

A polished demo is only the beginning. Engineering starts when you can locate the source of a behavior, name the state it changes, predict the side effects, make one controlled change, and prove that related behavior still works.

A large refactor can look cleaner while silently breaking taskbar state, leaving a camera active after its window closes, mixing unrelated files into a commit, or turning simulated portfolio claims into misleading ones. A valid result includes working behavior and evidence for why it works.

Essential question

How can one app move through open, focus, minimize, restore, and close while the DOM, taskbar, application state, and owned resources remain consistent?

Safety boundary

Do not mutate Serenity X while unrelated paths are staged, run an arbitrary proxy on a shared interface, enter real credentials into the demo, add dependencies, or use destructive Git commands. Resolve any difference between the worktree, target, and recorded plan before continuing.

Lesson objectives

By the end, you can

  1. Trace Calculator from its entry point through the registry, window creation, focus, minimize, restore, and close functions.
  2. Distinguish the registry, shared lifecycle state, application state, persistent storage, and acquired browser resources.
  3. Reproduce one existing failure, explain its mechanism, and make the smallest justified correction.
  4. Complete one architectural reduction and one resource-cleanup improvement without adding a framework or build step.
  5. Stage, review, commit, and push only one logical decision at a time while preserving unrelated work.
  6. Classify features as real, simulated, placeholder, unsafe, or removable and document one product decision.

Prerequisites and materials

  • Basic HTML and JavaScript: functions, objects, DOM elements, events, and variable scope.
  • The local Kush-Website checkout, Git, Node.js, rg, a modern browser, and browser DevTools.
  • Resolved file ownership and an explicitly reviewed scope before deleting a code path, changing the proxy, committing existing staged files, or pushing.

Glossary

Use precise nouns

Terms used in this lesson
RegistryThe data that gives each application an identifier, name, icon, and eventually its lifecycle callbacks.
LifecycleThe allowed states and transitions from not open to open, focused, minimized, restored, and closed.
State ownerThe one subsystem allowed to create and change a particular kind of state.
InvariantA condition that must remain true after every operation, such as one DOM window per open application.
Resource cleanupReleasing timers, media tracks, listeners, or object URLs when their owning application closes.
Vertical sliceOne behavior traced through every layer from user action to visible result, rather than one whole layer at once.
Staging areaThe exact snapshot Git will place into the next commit; it is separate from unstaged working-directory changes.

Mental model

One action, one state transition, several views

Opening an app changes more than the screen. The entry point selects an app, the app creates its content, the window manager creates a DOM window and updates openApps, and the topbar and taskbar render views of that shared state. Closing resource-owning apps must also release what they acquired.

desktop icon or launcher
  → openApp(id)
  → openCalc()
  → createWindow()
  → openApps[id]
  → focus / minimize / restore / close
  → topbar + taskbar views
  → app-specific cleanup when required

Persistent stateSeveral current systemslocalStorage, IndexedDB VFS, terminal FSThe current code does not yet have one storage owner.

Preflight

Inspect before mutation

Work from the root of your local Kush-Website checkout on serenity-x-deploy. Copy the output and interpretation into plan.md. If staged files outside Serenity X are present, resolve their ownership before the first Serenity commit.

cd path/to/Kush-Website
git status --short --branch
git fetch origin
git switch serenity-x-deploy
git pull --ff-only
git diff --cached --name-status
git log --oneline -- serenity-x
rg -n "var appReg|var openApps|function openApp|function openCalc|function createWindow|function focusWindow|function minimizeWindow|function focusOrRestore|function closeWindow" serenity-x/index.html

Stop conditions

Stop if a staged or modified path is not yours, a file differs from the plan, the branch is behind or conflicted, the agent proposes git add ., or any command includes reset --hard, clean -fd, repo-wide restore, rebase, or force push.

01

Map Calculator and the Git starting state

Inspect the actual system before changing it. Record the function trace and interpret each Git status column.

Gate — plan.md names each lifecycle function, the owner of window state, every unrelated staged path, the proposed commit scope, and the stop condition. No Serenity mutation has occurred.
02

Reproduce one failure before fixing it

Open the launcher, type a query, and use DevTools to capture the exact symptom. Trace callback scope before proposing a correction.

cd serenity-x
npm start
# In the browser: open the launcher, type "calc", and preserve the console output.
Gate — results.md contains the exact error, triggering action, source location, hypothesis, and unaffected behavior. Stop if the failure cannot be reproduced or a proposed fix changes more than the filter expression.
03

Make and review the smallest correction

Correct only the reproduced failure. Then test search by display name and identifier, followed by Calculator open, focus, minimize, restore, and close.

git diff -- serenity-x/index.html
git add -- serenity-x/index.html
git diff --cached --check
git diff --cached -- serenity-x/index.html
Gate — The staged diff contains only the explained correction; launcher search has no console error; the five Calculator transitions work twice; unrelated staged paths are not part of the proposed commit.
04

Remove one duplicate path

There are two context-menu elements and two overlapping control paths. Map every caller, choose the authoritative path, review the scoped diff, and delete only the redundant one.

rg -n 'id="context-menu"|showContextMenu|hideCM|bMenu\\(' serenity-x/index.html
git diff --stat
git diff -- serenity-x/index.html
Gate — The before-and-after map names both implementations and all callers. Desktop and browser context menus work in the intended states, the HTML has one context-menu ID, and no unrelated cleanup entered the diff.
05

Add an explicit cleanup boundary

Choose Monitor, Camera, or Voice Recorder. Trace what it acquires, prove what happens when its window closes, then add the smallest lifecycle cleanup mechanism.

rg -n "setInterval|clearInterval|getUserMedia|MediaRecorder|createObjectURL|revokeObjectURL|closeWindow" serenity-x/index.html
Gate — The chosen resource has a named owner and observable cleanup. Open/close it three times and show that timers, tracks, or object URLs do not remain active. Record one resource not yet covered.
06

Propose and perform one architectural extraction

Use the completed map to extract one stable boundary—prefer the app registry or Calculator—without a framework, package, build step, or big-bang rewrite.

find serenity-x -maxdepth 3 -type f -not -path '*/node_modules/*' -print
git diff --stat
git diff --check
Gate — The new file has one job, loads in a documented order, and preserves direct static use or explicitly records a changed run contract. The lifecycle smoke checklist passes before and after.
07

Audit product truth and attack surface

Classify all registered apps as real, simulated, placeholder, unsafe, or removable. Make one honest reduction or labeling change; do not attempt to harden a general-purpose proxy in this checkpoint.

rg -n "\\[Your Name\\]|simulated|Math\\.random|password|/proxy|self-contained|projData" serenity-x/index.html serenity-x/README.md serenity-x/server.js
Check — results.md contains the inventory and evidence. Real credentials were never entered. The proxy was not exposed for testing. One public claim or unsafe/removable feature was narrowed with a recorded reason.
08

Close out each decision with Git

One logical decision belongs in one commit. Read the staged diff, resolve unrelated work, review the message, push, and verify the remote.

git status --short --branch
git diff --cached --name-status
git diff --cached --check
git diff --cached
git commit
git push
git fetch origin serenity-x-deploy
git rev-list --left-right --count HEAD...origin/serenity-x-deploy
Gate — Each commit can be reverted independently, contains only its decision, has a clear message without AI attribution, and local/upstream divergence is 0 0 after the authorized push.

Change review

Use OpenCode as a reviewer, not an answer writer

Required

  • Inspect and cite evidence.
  • Use primary documentation.
  • State a bounded action and its effects.
  • Run the applicable checks.

Out of scope

  • Choosing a target or owner silently.
  • Broadening scope to make the result pass.
  • Deleting failure evidence.
  • Writing the student's plan, results, answers, or defense.

Investigation prompt

Help me reproduce and understand this failure. Do not edit anything yet.
Ask for my console evidence and identify the source locations I should inspect.

Bounded-change prompt

Review my proposed change against the recorded evidence. State the exact files,
expected effects, verification, stop condition, and recovery before editing.

Commit-review prompt

Review the staged diff for unrelated files and missing verification. Do not
write my results or explanation, and do not commit until I approve the scope.

Review

Compare proposed files with plan.md, read the complete staged diff, run the lifecycle checklist, and reject any success claim that lacks console, DOM/state, resource-cleanup, and Git evidence. OpenCode may implement, debug, explain, and review an approved bounded change; the student must write the predictions, observations, explanations, and defense in their own words.

Identify the failing layer first

Why not split the entire file immediately?

A large extraction changes file loading, global names, event order, state ownership, and many application paths at once. When it fails, the evidence cannot identify which boundary caused the problem. One vertical slice and one decision per commit make failure attributable and recovery cheap.

Walkthrough questions

  1. Starting at the Calculator icon, trace every function and state change until the window closes.
  2. Explain why minimized and closed are different states and show their evidence in the DOM and openApps.
  3. Reproduce the launcher failure, explain its mechanism, and describe why the correction is the smallest valid one.
  4. Show how the selected timer or media resource is created and released.
  5. Interpret both columns of git status --short and prove what the next commit contains.
  6. Explain the boundary you extracted and name one dependency that prevented a broader extraction.
  7. Explain one deletion or labeling decision from the product audit.
  8. Apply the same lifecycle model to another app and identify where the analogy breaks.

Completion criteria

  • Trace, simplify, test, and explain one complete app lifecycle.
  • The deliberate failure, one surgical reduction, one cleanup improvement, and one architecture boundary have inspectable before-and-after evidence.
  • Each Git commit contains one reviewed decision, with the staged diff and remote state recorded.
  • The product audit states what remains simulated, unsafe, or unresolved and transfers the lifecycle model to a second app.
